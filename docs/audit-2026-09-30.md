# Kalvora.js SDK — full audit (30 Sep 2026)

**Target:** `kalvora.js` v0.0.1-alpha.1, branch `fix/proto-change` (includes the `kal_guardian` proto rename).
**Method:** four specialist code reviews (crypto & key management; transaction builders & serialization; network, gRPC & wallet adapter; bridge/DEX/staking use-cases) plus automated checks (`npm audit`, `npm outdated`, vitest v8 coverage, dead-module sweep, unsafe-pattern grep, `dist/` inspection). Read-only; key findings were reproduced with throwaway scripts outside the repo.

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 4 |
| Medium | 18 |
| Low | 27 |
| Info | 20 |

Tests: 1,102 passing (55 files). Library-only coverage: **53.4 % lines / 77.1 % branches / 65.4 % functions** (the declared 80 % thresholds never fire — see R1).

## Verdict

No critical issues. The cryptography (exact SLIP-0010 Ed25519 pinned to the official vector, `@noble/*` and `bip39` only, no `Math.random` near key material) and the hash → sign pipeline are correct, and the transport layer resisted every endpoint-bypass probe. The four High findings are all deterministic correctness bugs in the layers *around* the crypto — identifier parsing, fee scaling, parameter encoding, and a missing outflow cap — and each can misroute funds or fees for real users. Fix them before anything leaves alpha. The Medium tier is dominated by missing input validation and trust-boundary gaps (node-supplied fees, guardian-supplied bytes, opaque signing payloads).

**Severity scale.** High = can misroute funds/fees or silently weaken key derivation; Medium = incorrect or unsafe behaviour under realistic input; Low = robustness, drift, or latent issues; Info = hygiene and documentation.
**Confidence.** Confirmed = reproduced or verified by reading the full path; Likely = code path verified, impact depends on wallets/nodes; Needs verification = depends on on-chain behaviour not in this repo.

Findings by area: Crypto & keys 12 (1 H / 2 M / 4 L / 5 I) · Transactions & fees 15 (1 / 3 / 7 / 4) · Network & adapter 14 (0 / 4 / 6 / 4) · Bridge, DEX & staking 17 (2 / 7 / 5 / 3) · Repo & process 11 (0 / 2 / 5 / 4).

## High-severity findings

### C1 · Public-key identifier parser mis-derives addresses for ~0.35 % of keys — Confirmed
**Location:** `src/shared/crypto/address-utils.ts:305-324`; consumers `src/coin-txn/transaction.ts:174`, `src/shared/tx/base.ts:75`, `src/adapter/wallet-adapter.ts:132`

`getHashTypesFromPublicKey` strips the `A_`/`B_` prefix and then treats any leading `a`, `b` or `c` as a hash-type prefix. Those are valid base58 characters, so a key-only identifier such as `A_cFkd…` is parsed as `[blake3]` and `generateAddressFromPublicKey` returns `base58(blake3(pk))` instead of `base58(pk)`. Brute force found 2 affected keys in 562 random Ed25519 keys. Downstream, `coin-txn` fetches the nonce for a non-existent address and the wallet adapter rejects a correct wallet with "address does not match its public key".

**Fix:** tokenise on `_`: after the optional `r_` and mandatory `[AB]_`, every intermediate token must be exactly `a|b|c` followed by `_`; the final token is the base58 body. The adapter already encodes this grammar as a regex at `wallet-adapter.ts:120` — make it the single source of truth. Add a regression test with the identifier above and an Ed448 analogue.

### T1 · Contract create/update scale `feeAmountParts` by 10^decimals — Confirmed
**Location:** `src/contract/create/transaction.ts:113`, `src/contract/update/transaction.ts:98`, `src/shared/fee-calculators/universal-fee-calculator.ts:755-756`

Both builders put `feeAmountParts` into `BaseTXN` correctly, then hand the same value to the fee calculator as `baseFee` (whole-token units) instead of `baseFeeParts`. `calculateNetworkFee` runs `toSmallestUnits` on it and overwrites `base.feeAmount`: reproduced `feeAmountParts: '1000'` → `base.feeAmount = '1000000000000'`. The example at `contract/create/examples/example.ts:980` promises the value is "used exactly". Every other builder uses `baseFeeParts`. `src/contract/**` has no tests.

**Fix:** change both spreads to `{ baseFeeParts: options.feeAmountParts }` and skip `calculateFee` entirely when `feeAmountParts` is set (as `vote` and `proposal-cancel` do). Better: migrate both builders onto `buildStandardTransaction`. Add a test asserting `base.feeAmount === options.feeAmountParts`.

### B1 · Delimiter injection: guardian- and user-supplied strings joined with `,` and `|` unescaped — Confirmed (SDK side)
**Location:** `src/smart-contracts/use-cases/bridge/kalvora/transactions/release.ts:233-247` (also `:79-87`, `:155-164`), `bridge/kalvora/transactions/lock.ts:72,154`, `dex/transactions/{swap:64,create-pool:63,add-liquidity:62,remove-liquidity:73,unlock-liquidity:54}.ts`, `staking/transactions/*.ts`, `bootstrapping/transactions/*.ts`

Every Kalvora-side builder builds the single `execute` parameter by positional `join(',')` and, for releases, `join('|')`. No field is escaped, quoted or validated anywhere in the chain. The most exposed path is `createSol`, whose `symbol`/`name`/`uri` come from Solana token metadata that the token creator controls; metadata URIs routinely contain commas (`data:application/json;base64,…`). A comma in `name` or `uri` shifts every later positional field (`walletAddress`, `amount`, `signedHash`). User-supplied fields (`toKalvoraAddress`, `walletAddress`, `platformFeeAddress`, token IDs) pass through verbatim too. No tests exercise these strings for any of the five bridge builders. On-chain exploitability depends on the contract parser, which is not in this repo.

**Fix:** add one `assertNoDelimiters(value, field)` that rejects `,`, `|` and control characters, applied in all four `create*Transaction` helpers; add `/^\d+$/` checks on numeric fields and base58 checks on addresses. Add parameter-string tests for `lockKalvora`/`burnSol`/`releaseKalvora`/`mintSol`/`createSol` plus negative tests. Ask the contract team whether free-text fields can move to a length-prefixed or JSON format.

### B2 · `allowances` outflow cap is never populated on any `SmartContractExecuteTXN` — Needs verification
**Location:** `src/smart-contracts/execute/transaction.ts:105-111`, `proto/txn.proto:518-529`, all use-case builders

The proto describes `SmartContractAllowance` as a user-signed per-execution cap on how much of each token may leave the wallet, with `unlimited` as an explicit opt-in. `buildSmartContractExecuteTXN` never sets `allowances`, the options type has no field for it, and no DEX/staking/bridge/bootstrapping builder sets it. If the chain treats an empty list as "no cap" — which the working e2e examples suggest — every swap, liquidity add, stake and bridge lock signs away unbounded outflow of every token for the whole nested execution tree.

**Fix:** confirm with the node team what an empty list means today. Add `allowances` to `BuildSmartContractExecuteOptions` and have each use-case set a tight default (lock/burn → the locked amount + fee token; swap → `tokenIn` amount; addLiquidity → both amounts; stake → the staked amount). Require callers to pass `unlimited: true` explicitly.

## What is working well

- **Key derivation.** Textbook SLIP-0010 Ed25519 pinned verbatim to the official test vector at all five depths; hardened-only enforced and tested; every primitive from `@noble/curves` 2, `@noble/hashes` 2, `bip39` with correct v2 APIs. `deriveHDPrivateKey` zeroes every intermediate node in `try/finally`.
- **Hash → sign pipeline.** `prepareBaseForSigning` clears both `signature` and `hash` before serialising; tests verify the signature against the reconstructed unsigned bytes and `hash === SHA3-256(signed bytes)`.
- **Standard transaction pipeline.** `buildStandardTransaction` uses strict parsers (`parsePartsAmount`, `parseUint64`, `parseHash32`, `parseAddress`) that reject `1e3`, `+5`, unsafe integers and out-of-range dates, plus a byte-determinism test and a post-build assertion that no signature material leaked.
- **Amount math** never touches floats — `Decimal` for conversions, `BigInt` for every Solana encoder and for USD→1e18 scaling in `allowance`.
- **Transport.** Protocol allow-list, credential rejection, URL redaction, `fallbackToHttp` immune to IPv4 shorthand tricks (runs on parsed `URL.hostname`); `KalvoraRpcError` preserves the real gRPC code and keeps `cause` non-enumerable; unsigned transactions refused before any network call.
- **Wallet adapter.** 128-bit `crypto.randomUUID()` request IDs, tab-scoped TTL'd `sessionStorage` records, single-use consumption before payload parsing, address derived from the key and compared, Android intents pin the wallet package.
- **Solana side of the bridge.** Free-text is length-prefixed Borsh, Ed25519 verify instructions built via `Ed25519Program.createInstructionWithPublicKey`, mint owner detected on-chain and unsupported token programs rejected before building, golden byte tests for lock/burn.
- **Smart-swap facade.** Strict envelope validation (type, version, base64, 1 MiB decoded cap), thorough negative tests, no private key crosses the indexer boundary.
- **Hygiene.** Server-keyed data kept in `Map`s (no prototype pollution); numeric strings parsed with `^\d+$` into `bigint`; live tests gated on an env var CI never sets; `proto:sync` is byte-exact and verified by `proto:check`; `public-api.test.ts` forbids legacy `Zera*` root exports.
