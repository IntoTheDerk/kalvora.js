# kalvora.js protocol migration handoff

**25 November 2026 · For kalvora.js maintainers.** The first release milestone is a wallet that can register on the fresh-genesis network and spend from that address in the next block. The SDK already sets signed transaction context and computes a post-signature hash. Its current builders still identify signers with inline Ed25519/Ed448 keys. Updating the generated types alone leaves those transactions unusable.

## 1. Sync and regenerate

Run these from the **kalvora.js root**, with its Node 20+ and locked dependencies installed in both the root and `proto/`. The SDK's read-only drift check currently reports all three public schemas. The SDK sync script accepts the directory containing the flat files. For an extracted handoff, substitute the extracted `kal_validator/proto` directory in both commands.

```sh
npm run proto:sync -- --source ../kal-network/kal_validator/proto
npm run proto:check -- --source ../kal-network/kal_validator/proto
npm run build:proto
```

| File | What the SDK consumes |
| --- | --- |
| [txn.proto](../../kal_validator/proto/txn.proto) | New `TXNService.RegisterWallet`, `WalletRegistration`, Falcon and policy types, registered signer fields, governance settings, votes, group outcomes and receipts. Registration is transaction **type 25**, block **TXNS field 30**, wrapper **oneof field 32**. |
| [kal_api.proto](../../kal_validator/proto/kal_api.proto) | New `APIService.GetSigningWallet` and `ProposalDetail`. `BaseFeeRequest.additional_signer = 3`. `ProposalStatus` fields 5–11 carry effective council lists, counts and active steps. |
| [validator.proto](../../kal_validator/proto/validator.proto) | Imported by the read API. Regenerate `POST_GOVERNANCE = 2`, granular votes, frozen ratios, PRE/POST state and snapshots. Closing, fanout and settlement messages also live here for validator storage and replay. |
| [falcon_genesis.proto](../../kal_validator/proto/falcon_genesis.proto) | Operator tooling for the signed format-2 launch artifact. `SignedLaunch` reserves old fields 2/3, holds owner/operator `RoleProof` at 4/5 and includes the operator's initial heartbeat proof. Wallet clients need the published genesis pin. |
| [wallet.proto](../../kal_validator/proto/wallet.proto) and [local_candidate.proto](../../kal_validator/proto/local_candidate.proto) | Validator storage helpers and local candidate-worker IPC, respectively. Wallet registration and registry queries are in the first two **public** files above. |

The SDK owns its existing `proto/guardian.proto` via a separate source. Its sync script retains the committed copy when syncing from kal-network. Regenerate it alongside the three public files with the existing Buf build. The SDK tracks the source protos and ignores `proto/generated/`. Carry new exports through `index.ts`, `wallet.ts` where applicable, `src/protocol/` and the package entry points.

## 2. Make a registered wallet's first payment work

**Identity and storage.** Update `src/wallet-creation/`, `src/shared/crypto/`, `src/shared/utils/validation.ts`, `src/sign/signer.ts` and `src/adapter/` together. Wallet files, injected providers, deep links, offline signers and WalletConnect integrations need to identify the selected wallet address independently of its Falcon public key. Persist the variant and hash selection with the key. Existing Ed key backups need a fresh Falcon key and deposit address for this genesis. Only advertise backup, restore and signing flows that work on each supported runtime.

| Variant | Raw public key including header | Detached padded signature |
| --- | ---: | ---: |
| `FALCON_512` | 897 bytes | 666 bytes |
| `FALCON_1024` | 1,793 bytes | 1,280 bytes |

Compute one selected digest of the complete canonical public key. Select `BLAKE3_256` explicitly by default. Support the eleven `WalletHash` values and store the complete 32, 64, 128, 256, 512 or 1,126 bytes. For `BLAKE3_9001`, apply `last_byte &= 0x80`. Display canonical Bitcoin-alphabet Base58, pass raw bytes in protobuf and use standard Base64 for protobuf JSON. Replace the SDK's short Base58 length checks across recipient input, query keys, grant parsing and storage. Two hash selections for one key can produce independent addresses, nonces and balances. [Address and signature formats](falcon_client_integration.md)

**Chain and registration.** Extend `src/sign/context.ts` with `WalletRegistration → REGISTER_WALLET_TYPE`. Configure `src/client/networks.ts` and each signer with trusted network identity. From height one, set `BaseTXN.signature_domain = ASCII("KAL_USER_TXN_V1")`, the concrete intended type, and the following raw 32-byte chain ID before fee sizing or signing. Use the operator's published **block-zero hash**, decoded from hex. The archive checksum, launch-file checksum and WalletConnect display ID serve other purposes. [Chain selection](chain_selection_and_ids.md)

```text
SHA-256(ASCII("KAL_CHAIN_ID_V2|") || ASCII("kal_main" or "kal_proto") || ASCII("|") || raw_final_genesis_hash)
```

The launch artifact uses separate manifest-bound signing domains for block zero. The SDK can derive the ordinary chain ID offline from a trusted name and final genesis pin. Two proto forks sharing block zero share this wire ID. [Working-tree implementation](../../kal_validator/crypto/attestation_network.h)

Build `WalletRegistration` with the derived address in `base.public_key.wallet_address`, explicit `wallet_hash`, and one identity arm, either `falcon { variant, raw_public_key }` or `policy`. A fresh single-key owner proves possession directly and can register using prefunded fees or a distinct registered single-key sponsor. A funded address can receive ordinary payments before registering. A registration finalized at height H enables spending, sponsoring and safe-send eligibility in H+1. The binding is permanent. The first nonce is 1. The raw Nonce RPC returns the committed value and the SDK's `src/api/validator/nonce/service.ts` already adds one. Coordinate owner and sponsor pending nonces separately.

**Proof assembly.** Update the shared base, serializer and finalizer before migrating individual builders. The main entry points are `src/shared/tx/base.ts`, `src/shared/tx/standard.ts`, `src/sign/finalize.ts`, `src/coin-txn/transaction.ts` and `src/validator-ops/transaction.ts`. Use the binary encoding of the concrete message. Preserve list order, presence of optional zero/false values, and serialized child payloads. After **all** applicable proofs are attached, clear only `base.hash`, serialize, then store the raw **SHA3-256** digest. [Signing rules](signed_transaction_context_v1.md)

| Operation | Signable bytes and proof placement |
| --- | --- |
| Single-key owner, including registration | Clear `base.hash`, `base.signature`, owner witnesses and the entire `base.fee_payer`. Sign and put the padded result in `base.signature`. Later transactions identify registered signers by address. |
| Sponsored base transaction | After the owner's proof, add the sponsor's address and nonce. Clear only the hash and sponsor signature for its countersignature. Store the proof in `base.fee_payer.signature`. Accept sponsorship only for the types in the [validator allowlist](../../kal_validator/headers/fee_payer.h), including wallet registration. |
| Registered policy | Register each single-key member first. Derive the policy address by hashing the ordered, big-endian length-framed `KAL_WALLET_MULTISIG_V1` descriptor. Members sign common owner bytes. Attach witnesses in strictly increasing slot order and leave the base signature absent. All class thresholds in any one pattern must pass. Reject duplicate underlying keys, including aliases. The policy uses its own nonce. [Descriptor and limits](falcon_client_integration.md) |
| Coin | Clear the hash, base signature, fee payer, **all** `auth.signature` entries and all authorization witnesses for the common preimage. Restore one signature slot per input. For a policy input put an empty byte string in that slot and the proofs in `auth.public_key[i].witnesses`. Keep authorization and allowance addresses/nonces aligned. For a Coin sponsor add a signed zero-amount input. Expose independent base-fee and contract-fee shares (`100000000` = 100% for each) and preserve the existing total fee caps. |

Opt-in `safe_send` in Coin, Mint and ItemizedMint requires every destination's registration in the finalized parent. The current Mint builder rejects `true`, and the Coin and item builders need a usable option. NFT transfer rejects `true`. Treat first-time token balance charges separately from signing-wallet registration.

For byte-level implementation questions use the [registered-wallet verifier](../../kal_validator/crypto/registered_wallet.cpp) and the [Coin and validator signers](../../kal_validator/crypto/signatures.cpp). For example, the existing SDK's operator helper signs `base.hash`, and its transaction hash helper clears `generatedSignature`. Both must change for a co-signed assignment.

**Fee quotes.** Update `src/shared/fee-calculators/`, `src/api/validator/base-fee/service.ts` and the gRPC wrapper. Replace the fixed 64/114-byte allowances with serialized placeholders for each actual padded signature, witness, countersignature and hash. Recheck the final encoded size including protobuf length prefixes and the decimal fee cap itself. If a signed cap must change, collect fresh signatures. Quote the primary signer with its selected witness count and pass the sponsor or validator co-signer as address-only `additional_signer`. Price Coin authorizations under the Coin rules. The node converts the byte, key and applicable safe-send components with separate ceilings, adds applicable stage charges, then applies the configured non-native multiplier. Apply operation-specific charges such as new balance rows. Check the shared root budget of 64 verifications, 256 KiB of authentication material and 8 MiB of verification input, including nested proposal children. [Fee calculation](../../kal_validator/block_process/fees.cpp) · [Authentication limits](../../kal_validator/headers/auth_resource_limits.h)

## 3. Update submission, reads and receipts

Wire the generated methods through `src/grpc/transaction/transaction-client.ts`, `src/grpc/api/validator-api-client.ts`, `src/query/api-client.ts`, `src/query/decoders.ts` and the public client facade. The sibling Docker Envoy configuration routes by service prefix.

| RPC | SDK behavior |
| --- | --- |
| `kal_txn.TXNService/RegisterWallet` | Map `kal_txn.WalletRegistration` to `registerWallet`. Native default port 50052, Docker gRPC-Web path `/txn/RegisterWallet`. The empty response acknowledges submission. Keep the locally computed hash for reconciliation. |
| `kal_api.APIService/GetSigningWallet` | Native default port 50053, browser path `/api/GetSigningWallet`. Send raw address bytes. A successful empty oneof means unregistered. Otherwise return the Falcon key or policy plus `policy_hash`. Propagate errors such as invalid address, unavailable storage or corrupt state. |
| `kal_api.APIService/ProposalDetail` | Browser path `/api/ProposalDetail`. Send the raw 32-byte proposal hash. Page size 0 selects 100, maximum 1,000. Follow `next_voter_offset` while `has_more`, passing the first page's `state_digest` as `expected_state_digest`. On `ABORTED`, discard partial results and restart at zero. `NOT_FOUND` means no active proposal record. Use committed history for its terminal outcome. |

For a transaction, match the receipt's `txn_hash` to the submitted `base.hash`, require the optional `status` to be present and inspect its value (`OK = 0`). Inclusion can carry a failed execution and a fee. Confirm finality against the expected chain and committee, or the application's trusted finalized source. Decode registrations in block `TXNS`, receipt `accepted_voting_ratio = 21`, and `SMART_CONTRACT_OUTPUT_TOO_LARGE = 45`. A governance child group can have one `GOVERNANCE_CHILD_GROUP_OUTPUT_TOO_LARGE = 8` marker at its first child with `terminal_group_child_count` and `terminal_group_sha256`. That covers all ordered siblings, with no per-child execution or fee. Respect optional `receipt_index`, including zero. After a timeout, reconcile the original hash, committed nonce and registry state. Within the signed time window (±10 minutes), retry identical bytes when appropriate. Re-signing a Falcon transaction can change its hash. [Client API](client_api_reference.md)

Replace Ed verification in `src/query/events.ts`. For signed contract replies, event pushes and signed search envelopes, match `public_key.wallet_address` to the expected validator operator, resolve its registered Falcon key, and verify the concrete protobuf with only its top-level signature cleared. Verify the signed search response around its stored events. When exposing paged search, bind its `request_digest` to the exact request and follow the opaque cursor. [Validator response verification](falcon_client_integration.md)

## 4. Migrate the remaining builders

| SDK area | Required behavior |
| --- | --- |
| `src/protocol/contract-id.ts`, `src/contract/create/`, `update/` and `shared/` | A wallet or policy creator uses `KALVORA_CONTRACT_ID_V2`, creator kind **4**, algorithm **0**, and the full length-prefixed wallet address. The sponsor and witnesses are outside the derivation. Internal smart-contract/governance creators use V1 kinds 2/3. Check the native ID and checksum with the existing genesis rules. Model direct restricted grants by wallet address and individual action flags. An inherited grant uses `parent_contract`, at most one parent, and a direct local `update_contract` recovery grant. Direct child entries take precedence. A nonempty update replaces the whole grant list. [Contract ID vectors](../../kal_validator/test/contract_id_vectors.json) · [Grant rules](restricted_key_inheritance_and_recovery.md) |
| `src/proposal/governance.ts`, `shape.ts`, `src/vote/` and contract governance settings | Add `GRANULAR = 5`. Require both thresholds in 1–10,000, 1–1,000 distinct raw voter addresses and an explicit whole-second voting window with start < end and end at most 90 days from acceptance. The optional instrument selects weighted voting. Preserve optional binary `support = false` and option index 0 (against). Zero-weight recorded ballots count toward participation. Granular votes are direct and have no councils. [Granular rules](client_granular_governance.md) |
| Regular voting ratios | For every regular voting instrument require one matching positive uint64 numerator/denominator pair. Freeze ratios at proposal acceptance. For each instrument and choice convert the aggregate once with integer floor of `raw × numerator / (denomination × denominator)`. NFT/SBT denomination is one. Use arbitrary-precision arithmetic and display receipt/result values in governance units. [Voting and ratios](client_governance_proposals_and_voting.md) |
| Council stages, votes and proposal views | Support singleton PRE or ordered PRE, public governance and ordered POST. With `allow_proposal_councils`, append proposal-specific stages after mandatory ones in each phase. Present-empty additional lists are invalid. Allow up to 32 effective stages per phase. Array PRE and every POST vote sign exactly one matching optional, zero-based step. A legacy singleton PRE without appended PRE steps also accepts an omitted index. Regular votes omit both. Use the proposal's frozen stage lists, active indices and pending indicators. Price each effective PRE/POST step with `ceil(base / divisor)` before the non-native multiplier, where divisor is stage-length count + 1 or 2 for an empty list. Wait for committed results and child outcomes before reporting execution. [Council lifecycle and fees](client_pre_governance.md) |
| `src/validator-ops/transaction.ts` and `src/query/validator-client.ts` | Use distinct registered single-key owner and operator wallets. For an assignment, set both owner fields consistently. Both roles sign the same unsigned assignment with hash, owner signature/witnesses, fee payer and `generated_signature` cleared. Attach owner and operator proofs **before** hashing. For deregistration omit both generated fields. A heartbeat uses the operational signature with the owner's nonce and fee, no sponsor or interface fee, maximum 64 memo bytes and 4,096 signed bytes. Track `last_signed_heartbeat_time_seconds` separately from producer liveness. Use `kal_validator.ValidatorService` for operator RPCs. BLS still signs consensus attestations. [Operator handover](falcon_wallet_handover.md) |
| `src/smart-contracts/` | For execute/instantiate, size signed gas and per-token allowances for the caller's actual debits and applicable contract fees. Contract-owned transfers of fee-bearing assets require the contract's fee-limit Wasm import. That permission belongs in the contract wrapper. Surface status 45 and charged compute on oversized output. Where an integration encodes grants for Postcard or calls the Wasm message verifier, use the typed grant identity and registered wallet address formats. [Native fee consent](../../docs/native-contract-fee-consent.md) · [Contract client formats](falcon_client_integration.md) |

## 5. Verify compatibility before releasing

For an ordinary validator join on this working tree, use native KALV as the fee instrument and wait for the on-chain validator registration fee policy to be installed. This prerequisite applies to `ValidatorRegistration`. Users onboard through the separate `RegisterWallet` path above. [Validator join fee policy](../../kal_validator/block_process/custom/process_registration.cpp)

1. **Check the frozen bytes.** The [Falcon vectors](../../tests/transactions/falcon_wallet_vectors.json) contain two keys with all eleven expected addresses and three signed registrations. Verify padded signatures, policy descriptor, serialized bytes and the hash with only `base.hash` cleared. Fresh randomized signatures should verify. Use the [contract ID vectors](../../kal_validator/test/contract_id_vectors.json) for both wallet widths, internal creators and native KALV.
2. **Have the validator execute JS output.** From the updated SDK export binary `registration.pb` (self-funded single key, nonce 1) and `coin.pb` (same base and authorization wallet, auth nonce 2, one input and one ordinary output of seven kalvs to another address). Use native KALV for the asset and fees, current timestamps and adequate caps. For this Linux fixture only, use `kal_main` and a genesis hash of 32 bytes of `0x47`. Its derived chain ID is `11390d9b4f1de05eefed175f4f1b562caffc85258007ba8d970a3ec28d29c1de`. Run the following with the validator build directory in `NODE_BUILD`. It checks settlement, replay and persistence across restart. [Native fixture](../../kal_validator/test/falcon_wallet_settlement_test.cpp)

   ```sh
   "$NODE_BUILD/falcon-wallet-settlement-test" --client-interop registration.pb coin.pb
   ```

3. **Exercise the public clients.** On a pinned rehearsal network finalize a sponsored zero-balance registration, a mixed-variant policy spend and a safe send across the H/H+1 boundary. Check the exact cap and one part below it, wrong-chain/type rejection, retry after timeout and confirmation by receipt. Cover raw wide addresses in query and adapter flows. Exercise granular pagination with a state change between pages, first PRE/POST step zero, one grouped child terminal marker, signed search response verification and the operator assignment with both signatures.
4. **Ship the public API together.** Run `npm run validate`, `npm run build` and `npm run build:validate-bundles` from kalvora.js. Update exported types, examples, adapter integration docs and release notes for the fresh-genesis wallet migration. Document how a user obtains a new receiving address, the trusted pin and the first confirmed registration.

**Checks performed for this handoff.** The SDK drift checker identified the three public files above. Using the SDK's installed Buf and protoc-gen-es, all four SDK modules generated in a temporary directory and the three new RPC input types resolved. All three saved registrations round-tripped byte-for-byte through protobuf JSON and binary and reproduced their hashes in JavaScript. The first Falcon-512 fixture hash is `aae7cd25f797268f48ea70b0cece4d7efbc81152af6cec1f0f33d1992242bcd4`. Separate synthetic Coin and granular proposal messages also matched C++ protoc's encoding. SDK implementation, new Falcon signing, the native settlement run with SDK-produced bytes and live endpoint tests are the receiving team's acceptance work.
