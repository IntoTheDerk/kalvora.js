# Falcon wallet migration handover

The implementation baseline on `will-sec-fixes-nov16` is `d0847db`, immediately after the branch's governance update `1d1e854`. It introduced registered Falcon signing wallets at **fresh genesis**. The format-2 launch build uses validator **200030**, attestation protocol **33**, with Wasm preparation gas enabled. The isolated comparison build uses **200031/34**. Operators, wallet teams and indexers must agree on the same signed genesis artifact and wire schema before launch. [Implementation commit](https://github.com/w-tw/kal-network/commit/d0847dbd339a2c01127ff026ad37f34af7284b91) · [Version policy](validator_version_policy.md) · [Third-party integration guide](falcon_client_integration.md)

## Protocol decisions to preserve

| Area | Maintainer contract |
| --- | --- |
| Wallet identity | Support padded Falcon-512 and Falcon-1024. One explicit hash of the complete canonical public key produces the full address. BLAKE3-256 is the client default. The same key can control independent addresses under different hash selections. |
| Receiving and authorization | A valid address can receive ordinary funds before registration, subject to the asset's rules. A registration in finalized block H can authorize spending, sponsorship or an opted-in safe-send destination in H+1. An address balance and a signing record have independent lifecycles. |
| Bootstrap and sponsorship | Verify a fresh single-key owner's proof from the registration payload. Charge its prefunded address, or verify a distinct registered single-key sponsor against the parent and charge the sponsor. Success consumes the owner's nonce and any sponsor nonce. Registry bindings are immutable. |
| Multisig | Register an ordered policy after all of its single-key members are eligible. Reject duplicate underlying keys, even across hash aliases. A valid subset signs against policy slots. The policy owns the spending nonce. |
| Validator keys | Keep an owner wallet for stake and assignments and a separate operational wallet for online signing. Require distinct underlying Falcon keys. This lets an operator keep the owner key offline between owner-authorized operations. The operational signer handles heartbeats, block envelopes, gossip, sync and signed replies. BLS retains its attestation key, proof of possession and aggregate verification path. |
| Contract authority | An ordinary wallet gets a privileged action through the target contract's typed `restricted_keys` grant. Governance and smart-contract execution authorities retain their typed paths. An explicit parent can delegate allowed actions. A direct entry on the child takes precedence, and an inheriting child must keep a direct recovery grant. Legacy `r_` identities and global restricted-wallet privileges retire at genesis. |

## Launch and validator operations

1. **Prepare the launch inputs.** Obtain the public owner and operator identities, hash choices, network name, timestamp, founder host and ports, BLS public key and proof of possession, ordered opening allocations and custody confirmation for the fee-treasury destination. Use clean data directories. Allocate at least 1,000,000,002 kalvs to the owner and two kalvs to the operator. Other recipients can register later. If the treasury will use an external key, confirm that its Falcon address derives to the configured destination before the ceremony. [Manifest format and treasury details](falcon_genesis.md)
2. **Collect the role proofs and pin the result.** Each custodian signs a nonce-1 wallet registration and the founding assignment. The operator also signs the initial heartbeat. Use `kal-validator --genesis-sign` for each role and `--genesis-assemble` with those exact proofs. Distribute the resulting `$DATA_DIR/config/falcon-genesis.pb` and independently verify the reported `CONSENSUS_GENESIS_HASH` on every node. Keep the exact public artifact and proofs. Re-signing can change block zero and the chain ID. [Ceremony commands](falcon_genesis.md)
3. **Check the first two heights.** At height 0 verify the two wallet registrations, assignment and heartbeat, all four receipts, the owner's final nonce 3, the operator's final nonce 1 and the archived founding committee. Verify the quorum certificate on the first ordinary block at height 1. For ordinary transactions the chain ID is SHA-256 over the network-name domain and final genesis hash. [Bootstrap implementation](../../kal_validator/attestation/consensus_bootstrap.cpp) · [Network and chain identity](chain_selection_and_ids.md)
4. **Onboard a later validator.** Provision the operational key with `kal-validator --prepare-operational-wallet 512 BLAKE3_256` or the selected variant and hash. Pre-register the owner and operator through a synced node and wait for finality. Configure `owner_wallet_hash`, `operational_wallet_hash` and `operational_falcon_variant`. Pin each seed as `endpoint|Base58RawFalconPublicKey[|WalletHash]` and, if setting `CONSENSUS_BOOTSTRAP_OWNER`, supply the founding owner's Base58 **wallet address**. In a validator assignment, `generated_public_key.wallet_address` names the registered operator. Both roles sign the same unsigned assignment bytes. The owner proof goes in `base.signature`, the operator proof in `generated_signature`. When rotating, register the replacement first, complete the owner-authorized assignment and update affected seed pins. Preserve historical assignments for replay. [Provisioning and pins](bootstrap_seed_pinning.md) · [Assignment verifier](../../kal_validator/crypto/signatures.cpp)

## Verification at the implementation baseline

The integrated commit passed **33 targeted checks**. Nine validator tests covered wallet vectors, registry recovery, settlement, signed genesis launch, genesis authority, attestation network identity, version policy and the branch's two signed governance replays. The other 24 comprised 22 concrete transaction field-binding tests and the schema and semantic accounting checks. [Wallet vectors](../../tests/transactions/falcon_wallet_vectors.json) · [Settlement and replay test](../../kal_validator/test/falcon_wallet_settlement_test.cpp) · [Genesis launch test](../../kal_validator/test/falcon_genesis_launch_test.cpp) · [Transaction test definitions](../../tests/transactions/CMakeLists.txt)

To repeat that selection in the Linux build environment, regenerate the C++/gRPC bindings as in the Dockerfile, build the root CMake project with testing and preparation gas enabled, and build the separate `tests/transactions` project with `KAL_TEST_LEDGER=ON` against the same `libkal-node.a` and generated headers. Set `NODE_BUILD` and `TX_BUILD` to those respective build directories.

```sh
ctest --test-dir "$NODE_BUILD" --output-on-failure --no-tests=error \
  -R '^(falcon-(wallet|registry-storage|wallet-settlement|genesis-launch)|genesis-authority|attestation-network|required-version-policy|item-deadline-signed-replay|council-phase-signed-replay)$'
ctest --test-dir "$TX_BUILD" --output-on-failure --no-tests=error \
  -R '^transaction-(binding[.]|schema-accounting$|semantic-accounting$)'
```
