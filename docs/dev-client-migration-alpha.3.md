# Migrating dev-client to kalvora.js 0.0.1-alpha.3

The first milestone is a user who can generate or restore a Falcon wallet, register its selected address, and see their first payment confirmed on the intended Kalvora network. Installing alpha.3 already gives the Electron client the new SDK exports. The client still builds and signs many Kalvora transactions itself, so a successful install covers only part of that milestone.

This guide compares the published `0.0.1-alpha.2` release with the alpha.3 source at `2a47020` and the Electron dev-client at `371221a`. Client paths below are relative to the dev-client repository. The separate Zera network uses its own SDK and protobufs. [SDK source comparison](https://github.com/IntoTheDerk/kalvora.js/compare/v0.0.1-alpha.2...2a47020439e6fae1c407897b4da3279f7f7366a5) · [Dev-client snapshot](https://github.com/w-tw/dev-client/tree/371221ae2d64c7e401fa7c939048e7225c000e0c) · [SDK verification and handoff](protocol-migration-overview-2026-11-25.md)

## What to do first

| When | Client work | How to tell it is done |
| --- | --- | --- |
| To run alpha.3 locally | Install the tarball and update three tests. Existing signed-envelope export and local single-key Falcon workflows are useful starting points. | The app reports `0.0.1-alpha.3`. TypeScript, lint, 129 tests and Windows x64 packaging pass. |
| Before testing real funds or calling a payment final | Configure the deployment identity, verify signed reads, save the signed envelope before sending, and confirm the receipt against a trusted finalized block. Check the actual proof layout and first-balance-row fee. | Registration at height H and a payment in H+1 each have a successful finalized receipt. A lost acknowledgement can be reconciled with the saved hash. |
| When migrating each additional screen | Apply the signing, field and fee rules below to the operations that screen exposes. Policy wallets, external signers and validator administration can be adopted independently of a first single-key payment. | The screen builds, signs and decodes the intended transaction with its real signers, network and fee budget. |

### Install and fix the three tests

From the sibling `dev-client` checkout with its dependencies installed, run the following PowerShell commands. The local tarball install preserves the manifest and lockfile. Once the package is published, use `npm.cmd install --save-exact kalvora.js@0.0.1-alpha.3` and commit the resulting manifest and lockfile in the client repository.

```powershell
npm.cmd install --no-save ../kalvora.js/kalvora.js-0.0.1-alpha.3.tgz
node -p "require('kalvora.js').VERSION"
npm.cmd run check
npm.cmd run package
```

| --- | --- | --- |
| `kal-signing.test.ts`, legacy unlimited allowance | The test constructs its old message with the currently installed SDK. Its alpha.3 schema has no `unlimited` Boolean and drops the property at runtime. | Construct the legacy input with a frozen alpha.2 descriptor or a decoded fixture retaining the old field. Keep the assertion that conversion yields `allowedAmount: "unlimited"`. |
| `kal-signing.test.ts`, retired grant field | The same fixture problem removes `RestrictedKey.timeDelay` before the converter can reject it. The unchanged client passed 126 of 129 runtime tests, including all eight mocked wallet and transaction tests, and packaged for Windows x64. In an isolated client copy, fixing only the fixtures and version expectation restored a clean type-check, lint and all 129 tests. Those edits still belong in the client repository. ## Network, protobufs and trusted reads

- **Keep the three Kalvora schemas in sync.** At these revisions, `dev-client/proto/kal/{txn,kal_api,validator}.proto` match the SDK inputs byte for byte. Regenerate the local `src/generated/kal/` bindings when those inputs change, or adopt `proto.txn`, `proto.api` and `proto.validator` where the SDK is already loaded. Registration is transaction type 25, block transaction field 30, and wrapper field 32. The SDK also regenerates its separately sourced guardian module. Keep historical descriptors used in migration tests versioned separately. [SDK protobufs](../proto) · [Client service routing](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/chain-kit.ts)
- **Bind each Kalvora connection to its deployment.** The client already derives a chain ID and stores it per endpoint. Its derivation accepts arbitrary printable network names. Use `deriveChainId` or `pinNetwork` with `kal_proto` or `kal_main` and the operator-confirmed final block-zero hash. Carry `transactionContext.chainId` on that connection. Supply the registered `trustedOperatorAddress` separately for signed reads. Keep the Kal and Zera selections explicit across IPC, imports and scripts. [Client network presets](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/shared/networks.ts) · [Client chain ID field](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/KalChainIdField.tsx) · [SDK network configuration](../src/client/networks.ts)
- **Configure the rehearsal gateway deliberately.** The client's built-in protonet hostname differs from the supplied `kal-stablenet.visiondynamics.ch`. For the existing short-path rewriter, configure the HTTPS **origin** so Balance becomes `/api/Balance` exactly once. The supplied read endpoint is HTTPS on port 443. Confirm the transaction route separately. The recorded attempt timed out before TLS. The supplied genesis and wallet values still need independent confirmation for this v35 launch. [Client RPC URL construction](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/validator-rpc.ts) · [Recorded gateway check](protocol-migration-overview-2026-11-25.md#verification)
- **Verify responses the UI presents as signed.** `getContract` and `searchSmartContractEvents` currently return raw RPC responses. Use a configured `createQueryClient` and its operator-aware methods. Resolve the trusted operator’s registered Falcon key, verify returned signatures, and bind paged event searches to the request digest and signed cursor. For active proposal voters, use `getProposalDetail` to obtain one consistent snapshot. Keep ordinary database lookups labelled as diagnostics. [Client operations](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/zera-client.ts) · [SDK query semantics](../src/query/README.md)
- **Preserve the existing block-by-hash path in alpha.3.** The client sends a Base58 block hash with `encoded: true`. The SDK’s `getBlock({ hash })` sends lowercase hex text with `encoded: false`, while the native reader uses the unencoded input as a raw database key. Keep the client’s Base58 route until the SDK conversion has a native round-trip test. SDK height reads can be used for receipt polling. [Client block lookup](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/zera-client.ts) · [SDK block lookup](../src/query/api-client.ts)

## Wallet registration and the first payment

| Step | What alpha.3 changes | What dev-client needs to do |
| --- | --- | --- |
| 1. Create and display a wallet | `FalconWallet` supports padded Falcon-512 and Falcon-1024. The raw key plus selected hash determines the receiving address. Eleven hashes produce six widths from 32 to 1,126 bytes. The default is BLAKE3-256. | The local generator already supports both variants and all hashes. Carry the selected Base58 address independently of the raw public key through the picker, vanity worker, IPC and forms. Preserve every byte, including wide-address padding. Test two addresses for one key. Existing Ed wallets need a fresh Falcon receiving address for this genesis. |
| 2. Restore an existing client backup | The SDK backup carries `networkName`, `genesisHash`, numeric `variant` and `walletHash`, `walletAddress` and a Base58 `secretKey`. | The client's `kalvora-falcon-keypair` export uses `network`, a derived `chainId`, enum names, `rawPublicKey` and `privateKey`. Add an importer that obtains the trusted genesis, recomputes the saved chain ID, maps the enum values and restores the key. Compare the derived public key and selected address with the saved values before accepting it. Test both variants and protect any exported secret material. |
| 3. Register a single key | `buildWalletRegistration` creates the unsigned registration. The owner signs. An eligible, distinct sponsor can countersign with its own registered address and nonce. Ordinary transfers can fund a fresh address before registration. | The client already supports self-funded and sponsored single-key registration and checks the returned Falcon identity. Preserve that behavior when moving to SDK builders. Persist the signed envelope and hash before issuing the RPC. Treat a registry lookup failure as unknown. |
| 4. Confirm registration and send | A successful registration in block H enables spending, sponsorship and safe receipt in H+1. A new wallet normally registers with nonce 1 and first spends with its authorization nonce 2. Coin signers approve the same transaction bytes in input order. | Fetch committed nonces, confirm registration at H, then make a small ordinary payment at H+1. Match the original hash to an explicitly present successful receipt status in a verified finalized block. Display the actual fee and updated balances. The existing client test simulates registration in memory. |
| 5. Recover a timed-out submission | Falcon can generate a different signature and hash when the same operation is signed again. The SDK supports bounded unary deadlines and receipt polling across a replaced provisional block. | Keep the client's Base64 envelope and hex hash on success and error. Capture the starting height and persist recovery data before submission. After a timeout, check the original hash, finalized receipt, registry and committed nonce. Retry identical valid bytes only when reconciliation warrants it. Use `waitForTransaction` with `verifyFinalizedBlock` backed by a trusted source. Keep the UI’s “Submitted” state until finality is verified. |

The work crosses the Electron renderer and main process. The registration panel owns review and display. The main process builds, signs, submits and returns recovery data. [Wallet generator and export](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/RawKeyPairPanel.tsx) · [Registration panel](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/FalconRegistrationPanel.tsx) · [Wallet and fee service](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/kal-wallet-client.ts) · [Signing service](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/kal-signing.ts) · [SDK wallets](../src/wallet-creation/README.md) · [SDK signing](../src/sign/README.md)

## Transaction changes by client feature

| Feature | SDK behavior and client action |
| --- | --- |
| Signing and offline envelopes | Set the signature domain, derived chain ID and concrete intended transaction type **before** fee sizing or signing. Use `getTransactionSigningBytes`, `getSponsorSigningBytes`, `signAndFinalize`, `countersignTransaction` and `finalizeTransactionHash` as appropriate. The final SHA3-256 hash covers attached proofs. A changed fee cap, timestamp or nonce requires fresh proofs. Rebuild historical signed transactions for the new network. In `kal-signing.ts`, keep wrong-chain/type rejection and envelope verification on import. |
| Policy wallets and external signers | Register the members first, then the policy descriptor. A policy owns its address and nonce. Collect the required witnesses in increasing registered slots. The client can inspect policy registrations and accept pre-signed envelopes. Interactive policy creation and witness collection need UI and signer integration. For injected wallets, deep links or WalletConnect, pass the selected wallet address and chain with the request. Check account switching when a single key has multiple addresses. [Policy registration](../src/wallet-registration/index.ts) · [Adapters](adapter-integration-guide.md) |
| Coin, amounts and fees | Pass the selected wallet addresses and signers to `buildCoinTXN` / `signCoinTXN`. Coin sponsorship uses a signed zero-amount input with separate base- and contract-fee shares. An allowance spend has distinct spender and source nonce handling. Use the actual denomination, integer arithmetic and the contractual fee instrument for conversion. The client already supplies denominations, but `calculateKalFee` reserves a 1,280-byte proof per signer, a 78-digit cap, and a new-wallet fee per output. Use the actual Falcon variants, policy witness slots, sponsor and first-balance-row facts for fee comparisons. Re-sign after changing the priced bytes. [Client Coin path](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/main/services/zera-client.ts) · [SDK Coin builders](../src/coin-txn/README.md) |
| Recipients and safe send | Coin, Mint and ItemizedMint support safe send. NFT transfers reject it. Apply recipient rules for the operation, including wide wallets, padding, burn and proposal escrow where permitted. The client's ordinary Coin output currently passes through its wallet-only decoder, so a permitted burn output needs a distinct check. Do not show the safe-send option on an operation that cannot encode it. Test an unregistered destination, H/H+1, and an existing versus new token balance. [SDK address and query rules](../src/query/README.md) · [Client asset form](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/AssetTransactionForm.tsx) |
| Instrument creation, updates and grants | Wallet and policy creators derive V2 contract IDs from the complete creator address and vanity nonce, including default zero. Internal governance and smart-contract creators retain V1. The client already derives a V2 ID. Its local builder bypasses SDK validations, and its TOKEN test omits `maxSupply`. Validate supply, denomination and premints before signing. Map direct wallet and parent-contract grants, reject duplicate authorities and self-parent links, and preserve a local recovery authority. A nonempty update replaces the entire grant list. Review the complete replacement with the user. [SDK contracts](../src/contract/README.md) · [Client contract form](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/InstrumentContractForm.tsx) |
| Retired operations and fields | Alpha.3 removes Quash builders and the transaction type. Remove Kalvora routes and presets for Quash and reject retired `timeDelay`, `global`, `quash` and `quashThreshold` before protobuf conversion drops them. Review shared dispatch tables by selected chain. Revoke, compliance, allowance, expense ratio and delegated voting use the registered signing context. |
| Governance | Support granular binary and option voting, frozen per-instrument ratios, and ordered PRE and POST council steps. Preserve explicit NO, option zero and step zero. Include the applicable council-step fees. Adaptive proposals enforce the 90-day bound and council restrictions. Read the active phase and voters with `getProposalDetail`. Use committed block results for completed proposals, including multiple steps in a v35 block and grouped child outcomes without an individual receipt. Map these fields into the proposal, vote, cancel and result views. [SDK governance](../src/proposal/README.md) · [Client proposal form](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/GovernanceProposalForm.tsx) · [Vote form](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/renderer/components/GovernanceVoteForm.tsx) |
| Smart contracts, DEX, staking and bridges | Execute and instantiate accept per-token caller budgets with `allowedAmount` as a uint256 string or the exact literal `"unlimited"`. Omitted tokens have zero budget. Include token fees in the authorized debits and expose the signed network/gas cap. A contract spending its own balance on fee-bearing assets needs the appropriate Wasm `*_with_fee_limit` call. Check each wrapper’s source network, registered signer, allowances and fee preview before enabling its convenience action. The current generic client dispatcher blocks Kalvora actions that sign and submit internally. Enable validated actions individually. [SDK smart contracts](../src/smart-contracts/README.md) · [Client operation catalog](https://github.com/w-tw/dev-client/blob/371221ae2d64c7e401fa7c939048e7225c000e0c/src/shared/transactions/catalog.ts) |
| Validator administration | If adding this workflow, keep it separate from user onboarding. Validator registration requires registered owner and operator roles signing the same assignment, with both proofs in the final hash. Deregistration uses the owner. A heartbeat uses the operator’s signature and the owner’s nonce, with 64-byte memo and 4,096-byte signed size limits. Show producer liveness and last signed heartbeat separately. BLS attestation key/proof inputs have fixed lengths. A v35 join also needs the native KALV fee policy in place. [SDK validator operations](../src/validator-ops/README.md) |

## Acceptance checklist

- [ ] **Package and fixtures.** Pin the release on the client integration branch. Verify the SDK version, both legacy conversion fixtures, all 129 tests and a Windows x64 Electron package. The SDK requires Node 20.19 or newer. Use the client’s own supported Node version for Electron builds.
- [ ] **Offline wallet and payment.** Restore a client-exported wallet with the correct network pin, reject a mismatched pin, and verify each Falcon variant and a wide address. Check exact and one-part-low caps, nondecimal denominations, mixed signers, first balance creation and a cap change after signing.
- [ ] **Read-only rehearsal.** Obtain the deployment’s verified genesis, operator address and reachable routes. Confirm block zero and version, a verified contract reply, correct event pages and receipt polling by height. The target reported for rehearsal is validator `200032`, protocol 35.
- [ ] **First live payment.** Prefund a fresh address for registration, the transfer amount and fees. Record registration at H and its first outgoing payment in H+1. Separately exercise a zero-balance sponsored registration. Fund that wallet with an ordinary transfer before its first spend and cover its fee from that balance or a separate Coin fee input. Reconcile each finalized receipt, nonce and balance with the saved hash. Demonstrate recovery after a lost acknowledgement.
- [ ] **Additional enabled features.** Test mixed-variant policy spending, safe send across the registration boundary, a V2 contract and replacement grants, governance paging during a state change, step/option zero and grouped results. Add a dual-signed validator assignment or external-wallet round trip when that feature is exposed.

Offline Linux v35 fixtures already settled SDK-generated registrations, payments, sponsorship and policy spends and reproduced state after restart. The public gateway rehearsal remains open.
